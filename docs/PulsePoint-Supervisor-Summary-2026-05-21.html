Executive summary

Today’s work established PulsePoint, a modern, modular association management system (AMS) aimed at healthcare member-based organizations. The project is positioned as a long-term alternative to legacy AMS products (e.g., Protech-scale cost and implementation timelines), with a deliberate foundation-first approach: multi-tenant data isolation, audited actions, controlled data migration, and honest public positioning of what is live versus on the roadmap.

One sentence for boards and grants: PulsePoint ships MemberCore (membership management) and PulsePoint Events (registration and check-in) as the live wedge; additional modules (Learn, Commerce, Insights, Giving, Engage) are labeled Alpha / Roadmap until they pass formal go-live gates—not implied by marketing alone.

This is not a superficial demo site. It is a working prototype with association-grade plumbing (tenant scoping, permissions, payment webhooks, import review workflows, and CI quality gates). The platform is designed for PII only (member contact and event data)—not clinical PHI—so the organization does not accidentally become a HIPAA-regulated health data platform.

Strategic intent (what we set out to build)

  • Problem: Legacy AMS contracts are expensive, slow to change, and bundle modules many associations never fully use.
  • Solution: A modular platform the organization can own and extend—starting with the highest daily-use capabilities: members + events.
  • Delivery model: Multi-tenant SaaS architecture from day one (each association’s data isolated by organization ID).
  • Scope discipline: We are not cloning twenty years of legacy edge cases in one release; expansion is gated module-by-module.
  • Competitive reference: Product structure aligns with familiar AMS categories (membership, meetings/events, education, fundraising, commerce, marketing, analytics) while marketing honestly labels Live vs Roadmap status.

3. Engineering and risk controls (anti–“vibe code”)

  • Multi-tenant isolation: All member and event data scoped per organization; automated leak checks and tests.
  • Server-side permissions: Sensitive actions (export, import apply, delete, money paths) require real capabilities—not UI-only checks.
  • State machines: Event registration and payment transitions enforced in code.
  • Webhooks: Stripe (and Clerk when used) with signature verification and idempotency to prevent double charges.
  • Audit logging: Imports, exports, deletes, registrations, and payment-related actions recorded.
  • Security: Rate limits on public registration; security audit script in CI; documented contributor rules for auth and payment code.
  • Claims validation: CI checks marketing copy against a product-claims registry so decks cannot drift ahead of shipped code.

4. Documentation for leadership, IT, and operations

  • Project brief, scope wedge, operator checklist (red/yellow/green), runbooks, subprocessors table, deploy guide, free-stack and demo-mode guides.
  • Clear positioning: what may be said publicly today versus what remains roadmap.

5. Local prototype ergonomics (today’s refinements)

  • Standalone demo: Removed dependency on paid Clerk for local leadership walkthroughs when DEMO_MODE=true.
  • SQLite local database: No Docker required for prototype—pnpm demo:setup seeds a file-based database.
  • Fixed middleware, branding, and routing issues so /demo → Enter demo → /demo-healthcare works without username/password prompts.

Timeline expectations (realistic)

  • Today: Working prototype suitable for leadership walkthrough via demo mode and local install.
  • Next 2–4 weeks (part-time focus): Pilot-ready MemberCore + Events—production deploy, Stripe end-to-end test, named runbook owners, privacy counsel review.
  • Additional modules (Learn, Commerce, Insights, etc.): Each requires roughly weeks to months per module at the same quality bar—not a one-week “add everything” effort.
  • Full Protech parity: Explicitly out of scope for v0.1; would be a multi-year product program, not a single sprint.
